## 2. 角色 + 池子模型

### 角色定义(`roles/*.md` frontmatter)

| Role | type | 是否池化 | 上限 |
|---|---|---|---|
| **mate-R** | requirements | **per-thread** — 每条线索独占一个 R inst | `parallelism_limit: 10` |
| **mate-H** | orchestrator | **pooled** — 每 project 内共用 1 个 | `parallelism_limit: 1` |
| **mate-B** | executor | **pooled** — 每 project 内可 4 个并发 | `parallelism_limit: 4` |
| **mate-C** | validator | **pooled** — 每 project 内可 4 个并发 | `parallelism_limit: 4` |

**关键点**:H/B/C 是**跨线索共用的池实例**,一个 H 会依次处理不同线索的活。这就是所有 chain 走串 bug 的根源土壤 — 同一个 `inst.threadSlug` 字段被多条线索复用。

### Instance 关键字段

```js
{
  id: 'mate-H.lo335h',        // 唯一,含随机 6 位后缀
  displayName: 'mate-H-1',     // UI 友好名,用 poolSlot(H 只 1 slot)
  role: {name, type, ...},
  projectId: 6,
  status: 'idle' | 'busy' | 'spawning' | 'disconnected' | 'dead',
  threadSlug: 't-mrxxx-...',   // ⚠ 会被 dispatchCb 翻,是所有 race 的靶心
  currentTaskSlug: 't-mrxxx',  // UI 显示用,同 threadSlug
  poolSlot: 1,                 // pool 分配的槽位
  sessionId: 'uuid',           // claude CLI session
  _currentPendingSend: null,   // 当前正在跑的 queue 项
  _pendingUserText: null,      // spawn 时的首条 stdin
}
```

## 3. 派工链路(User → R → H → B/C → H → User)

### 3.1 User → R(直发,per-thread)

```
浏览器提交:POST /api/threads/:slug/message  text
    → SpawnManager.sendToThread(...roleType='requirements'...)
      → _sendToPerThreadRole(...)
        → 找/建 R inst(该线索独占)
        → inst.sendUserText(text)  → 写 claude stdin
```

**特点**:R 是 per-thread,不排队 — 一个 thread 只有它自己的 R,不会跟别的线索抢。

### 3.2 R → H(marker 派工,pooled)

R 的输出 assistant text 里包含 `<mate:handoff target="mate-H" reason="..." />` → MarkerDetector 识别 → MarkerDispatcher._performHandoff:

```
1. append 一段 handoff seg 到 dispatch_chain(#186 修:必须先追加)
2. sendToThread({roleType:'orchestrator', fromMarker:true, markerFromInst:R, ...})
   → _sendToPooledRole(...)
     → PoolAllocator.acquire() 找 H(pool_slot=1)
     ┌─ H idle/disconnected → 直发 stdin(sendUserText),同时 inst.threadSlug=新 thread
     └─ H busy → QueueDispatcher.enqueueDispatch()  →  pending_sends 表加一行
        (queued 状态,等 H idle 时 flush)
3. replayChain 重算栈,写 call_stack_json
4. DispatchLogWriter 落派工文件到磁盘 <project>/doc/_dispatch/...
```

### 3.3 H → B/C(同上,pooled)

跟 R→H 一样,只是 target 换成 B/C。

### 3.4 B/C → H(callback,弹栈)

B/C 完事后 emit `<mate:handoff target="mate-H" reason="实施完成..." />` — mate 识别为 **callback**(B/C→H 的固定语义):

```
- chain append 一段 handoff(callback 语义)
- 栈:pop B/C 帧
- 消息发给 H,H 接着做验收
```

### 3.5 H → User(terminal done)

H 觉得任务完了,emit `<mate:done summary="..." />` → MarkerDispatcher._performDone:

```
1. 找 caller(栈 lookup:栈里 H 帧下方那一层)
2. isTerminal = caller 是 R 或者栈空
3. append done seg to chain
4. replayChain 派生栈
   - terminal:清空栈,outcome=verified,stage=verified
   - 非 terminal(caller 是 H,不可能但兜底):pop 一层
5. 给 R 注入系统消息 [<delegate mate-H-1 done>] <summary>
6. R 翻译给 user
```

## 4. 排队机制(pending_sends 表)

### 4.1 为什么需要排队

**5 种触发条件**(reason 字段):

| reason | 场景 | 谁触发 |
|---|---|---|
| **`busy`** | R→H 时 H 正在跑别的线索,H stdin 排队 | QueueDispatcher.enqueueDispatch |
| **`quota_pause`** | 5h/7d 撞墙,mate 主动 pause,新 send 入队等 reset | sendToThread quota gate |
| **`quota_mid_turn`** (#176 Layer 1) | H 处理途中 claude 撞 429,mate 兜底重发 | `_handleMidTurn429` |
| **`session_lost`** (#180 Layer 4) | claude CLI 忘掉 old session(`--resume` 失败),mate 换 fresh session 重发 | `_handleSessionLost` |
| **`spawning`** | (预留,暂未启用) | — |

### 4.2 排队条目形态

```js
{
  id: 27,
  kind: 'handoff_marker' | 'thread_send' | 'direct_send',
  target_kind: 'instance' | 'thread',
  target_id: 'mate-B.a5g7pb' | 't-mrxxx',
  thread_slug: 't-mrx143jk-xva2',    // 关键 — flush 时会 set inst.threadSlug
  status: 'queued' | 'waiting_user' | 'backlog' | 'processing' | 'cancelled',
  reason: 'busy' | 'quota_pause' | ...,
  from_instance_id: 'mate-H.lo335h',  // 派工者
  payload_json: { text, ... },
  enqueued_at, processed_at, cancelled_at,
}
```

### 4.3 Flush 触发点(修复 #194 后)

**Path A:status_change → idle 的非 busy 转换**(#191 加的过滤)
- `spawning → idle`(spawn 完系统 init)
- `disconnected → idle`(极少)

**Path B:result 事件后的 setImmediate(#188 + #194)**
- 任何 turn 结束都触发,markers 处理完后再 flush,不会翻 threadSlug 干扰 markers 处理

**Path C:quota resume**(#167 + #173 + #176 + #180)
- QuotaState._performResume → `system.quota_resumed` 事件 → `SpawnManager._flushQuotaPaused`
- 按 enqueuedAt FIFO 处理所有 reason ∈ (quota_pause / quota_mid_turn / session_lost) 的项

### 4.4 状态机

```
enqueue → queued
   ↓
   ├─ waiting_user (busy 时用户没决定 wait/backlog/cancel — Phase 2G 老路径)
   ├─ backlog (用户选"稍后派")
   └─ processing (dispatchCb 拿走,即将 sendUserText)
              ↓
              ├─ removed (dispatch.completed 触发,inst 完成本轮 result)
              └─ cancelled (flush 出错)
```

## 5. 回调 / 状态机(Chain + Stack + Replay)

### 5.1 双 SSOT(**这里是关键设计**)

**`dispatch_chain`**(存 thread.metadata_json 里,append-only)
- 只加不改,每次 handoff/done/blocked/reject 追加一段
- **纪实**:mate 生存的完整历史

**`call_stack_json`**(存 threads 表 call_stack_json 列)
- 由 chain 派生(**不双写**,#191 后完全 derived)
- **当下**:目前谁在跑,谁等谁

### 5.2 replayChain — 单一真理来源

`replayChain(chain, opts)` → `{ stack, outcome, warnings }`

- 从 chain[0] 开始重放:
  - `handoff` push down(R→H 或 H→B/C)、pop callback(B/C→H)、bounce(H→R)
  - `done` isTerminal:清空栈 + outcome=verified;非 terminal:pop 一层
  - `blocked` 栈顶 status=blocked + pendingQuestion
  - `reject` pop self + 栈空 → outcome=aborted
- 输出的栈永远跟 chain 一致(**不可能累积漏洞**)

### 5.3 Marker 处理契约(修 #175/#186 后)

```
_performXXX():
  1. 各种 guard(#175 loop guard:outcome=verified/栈空/fromInst 不在栈 直接 no-op)
  2. 【必须先】ThreadStore.appendDispatchChain(...)  ← #186 时序修复
  3. _updateStack(...)  内部实为 replayChain(最新 chain)→ TCS.save
  4. recordEvent + DispatchLogWriter 落派工文件
  5. 触发下一动作(注入 R / 派工 B / bounce 等)
```

### 5.4 已知 chain 走串场景(全部已修)

| # | 场景 | 修复 |
|---|---|---|
| #175 | R↔H done 死循环 | 三层 guard + prompt 反模式 |
| #186 | _updateStack 时序错(先 update 后 append,读到旧 chain) | 4 处调换顺序 |
| #187 | queue flush 不翻 `inst.threadSlug` | dispatchCb 加翻 |
| #188 | flush setImmediate 抢在 markers 前跑 | 移到 event handler 末尾 |
| #191 | busy→idle 同步 flush 翻 `inst.threadSlug` → 后面 recordMessage/markers 用错值 | status_change idle 只处理非 busy 转换 |
| #193 | `<title>` 里 currentActivity 未 escape → `<mate:handoff>` 破坏 SVG DOM | escapeHtml |
| #194 | #191 阻止 busy→idle flush,#188 只在 pending_send 时触发 → 直发 turn 完成不 flush | 任何 result 都 flush |

## 7. 需要加强的地方(排序:优先级由高到低)

### 🔴 高优先级 — 稳定性

**A1. `inst.threadSlug` 不该是 mutable 字段** — 是所有 chain 走串 bug 的靶心
- 建议:改成"每 turn 有一个 pinned threadSlug",通过 `inst._currentTurnThreadSlug` 或 pending_send 里存
- 或至少加锁:`inst._turnInProgress` 期间不允许其它 code path 翻它
- 目前修法(#187/188/191/194)是在时序上绕开,不是彻底解决

**A2. SpawnManager god class(1365 行)** — arch-debt §1
- 派工、排队、生命周期、事件透传、TTL 扫描、pool 分配全塞一起
- 修一处 bug 常常改其它路径的行为(#191→#194 就是这样)
- 建议:拆成 `InstanceRegistry` / `DispatchOrchestrator` / `EventRouter` / `TurnLifecycle`

**A3. 竞态测试基础设施缺失**
- 目前所有并发 bug 都是**用户在真实场景撞出来后才发现**
- 建议:写基于 `MockRoleInstance` 的测试,模拟"H 处理 A 的时候 R-of-B 派工"这类场景
- 加 `MATE_MOCK_TERMS=1` E2E 测试组合场景

**A4. 双 SSOT 一致性检查**
- chain(append)和 stack(derived)偶尔会漂移(见早期脏 stage bug)
- 建议:加个后台 cron,每小时全库 `replayChain(chain) vs db.stack` diff,不一致就修 + 报警
- 目前的 `scripts/scan_chain_crossings.js` 只查 chain 内容,不查 stack 一致

### 🟡 中优先级 — 可观测性

**B1. 更结构化的事件日志**
- 目前 `events` 表只记业务事件,没记"race 疑似发生"这种诊断线
- 建议:关键 mutex 点(threadSlug flip / status change)记 `debug.mutation` 事件,遇 bug 可回放

**B2. Dashboard "Chain 自检" 加上滚动扫描历史统计**

**B3. 前端 UI 状态一致性问诊工具**

**B4. mate 后端结构化日志**
- 目前很多 `console.warn` 是散的

## 8. 方法论(反思)

前几周踩了 chain 走串 4 轮才根治(#187 → #188 → #191 → #194),原因:
1. **只看到表面症状就改** — 应该先画完整并发时序图
2. **不做实测就宣称修复** — 应该改完必跑 `scan_chain_crossings.js`
3. **不用 headless 抓真实 DOM** — 让用户来回贴 devtools 输出,浪费时间

**今天开始的新工作方式**:
- 遇 UI bug → **playwright headless 直接抓 SVG innerHTML + DOM 状态**,一次定位
- 遇后端并发 bug → 修完必跑对应的诊断脚本(`scan_chain_crossings.js` 目前是唯一,应扩)
- 关键改动必写"验证方法"(重启后运行什么 → 期望什么输出)
