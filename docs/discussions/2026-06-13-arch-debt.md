## §1 SpawnManager 是 god class(1080 行,9 个职责)

**位置**:`server/spawn/SpawnManager.js`

**问题**:单个 class 承担:
1. 实例池管理(acquire / release / pool_slot)
2. RoleInstance lifecycle wiring(`_wireListeners`)
3. marker dispatch(`_handleMarkers` / `_performHandoff/Done/Blocked`)
4. handoff 进度状态机(`_pendingHandoffReady` Map → `.spawning/.ready/.failed`)
5. clientMessageId FIFO(乐观 UI dedup)
6. TTL scanner(`_runTtlScan`,3 个子分支 — ttl_warn / stuck busy / disconnected 老化)
7. global cap warn(`_checkGlobalCap`)
8. QuotaState wire(`inst.on('event')` 路由 `rate_limit_event` → ingest)
9. 持久化 + bus.publish 桥接(`_persistInstanceUpsert` / 全部 publish 都在这)

**风险**:再加任何能力(§3 排队 flush / §6 quota 暂停拦截 / multi-API key 切换)都往这堆,1500 行后没人敢动。

**建议拆分**(Phase 2F+ 路过时做):
```
SpawnManager.js (~300 行)        — 核心 spawn + 实例池 lookup + lifecycle 桥接
├─ PoolAllocator.js (~200 行)    — _acquirePoolInstance / _findNextFreePoolSlot
├─ MarkerDispatcher.js (~200 行)  — _handleMarkers / _performHandoff/Done/Blocked
├─ HandoffTracker.js (~150 行)    — _pendingHandoffReady 状态机(spawning/ready/failed)
└─ ScanRecycler.js (~200 行)     — _runTtlScan + stuck busy + aging + global cap
```

各取一份职责,SpawnManager 主类只负责 wiring。

## §3 `db.js` 含 `recordMessage` / `recordEvent` 业务函数(L0 → L1 漂移)

**位置**:`server/db.js` 末尾

**问题**:`recordMessage(msg)` / `recordEvent(kind, payload, opts)` 是业务 store 函数,但写在 L0 infrastructure。违反 §3 模块拓扑(L0 不依赖业务实体)。

**为什么**:历史包袱 — Phase 1 没拆,prepared statements 在 db.js 顺手 export 了 helper。

**建议**:Phase 2F+ 新加业务持久化函数 **必须**去 L1(例如造一个 `MessageStore.js` / `EventStore.js`)。**老的 recordMessage / recordEvent 暂不动**(动它要改 N 处 import,风险大于收益)。

**影响**:目前 17 处 require `recordMessage`,9 处 require `recordEvent`。

## §5 `ThreadHooks` 反向 require `SpawnManager`(L3 → L2 循环依赖风险)

**位置**:`server/system-agent/ThreadHooks.js` 实际 require 链需确认

**问题**:L3 模块按 §3 模块拓扑应**只允许向下依赖** L0-L2,但 ThreadHooks 在 result event 处理时,通过 `SpawnManager._wireListeners` 间接被调,而 ThreadHooks 内部也可能反查 SpawnManager 状态(取决于 reply-template 是否需要看 pool state)。

**当前状态**:未发现真循环 require(node module cache 容忍),但语义上反向 dependency 已经存在。

**建议**:
- 用 messageBus 解耦:SpawnManager publish `result.ready`,ThreadHooks subscribe + 跑 SystemAgent + publish `thread.metadata_updated`
- 或:把 result-after hooks 移到 SpawnManager 内部小函数(L2 内),ThreadHooks 只剩 reply-template 等纯 metadata hook

Phase 2F+ 评估。

## §6 缺统一 `EventStore` L1 模块

**问题**:无统一 store,新事件类型 / 新读取路径都得绕开本应的封装层。

**建议**:Phase 2F+ 加 `server/events/EventStore.js`(L1)统一 list / filter / aggregate。老的 recordEvent + 散落的 SELECT 渐进迁移。
