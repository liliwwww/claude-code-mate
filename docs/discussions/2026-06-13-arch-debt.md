## §2 `public/app.js` / `dashboard.js` 单文件巨石 ⏸ 暂不修(2026-06-13 决定)

| 文件 | 行数 | 混合的关注点 |
|---|---|---|
| `public/app.js` | 954 | state + WS + send + render + project picker + thread CRUD + dialogs + markdown + tool block + handoff card + 乐观 UI + theme + ticker + banner |
| `public/dashboard.js` | 759 | 4 tab + 各 tab render + mateTerm dual mode + WS dedup + chip init |

**决定不修的理由**:
1. 0 build 约束下,拆 IIFE 只能靠 `window.MateApp.*` 命名空间,引入间接
   层,可读性反降
2. 所有方法**深度共享 state**(`state.threads` / `state.instances` /
   `els` 等),拆开后 state 传递更复杂
3. 当前没有"加 1 个功能破坏 10 处"的退化迹象 —— 不是真痛
4. 等以后真痛了再说 / 或者哪天引入 build chain(违反当前 0 build 约束,
   要先开会)

**触发条件**(满足之一就重启 §2 讨论):
- app.js 突破 1500 行
- 同一份 state 在多文件被改(已经"被迫"分文件)
- 加新功能需要改 5+ 处分散点
- user 引入 build chain

## §5 `ThreadHooks` 反向 require `SpawnManager`(L3 → L2 循环依赖风险)

**位置**:`server/system-agent/ThreadHooks.js` 实际 require 链需确认

**问题**:L3 模块按 §3 模块拓扑应**只允许向下依赖** L0-L2,但 ThreadHooks 在 result event 处理时,通过 `SpawnManager._wireListeners` 间接被调,而 ThreadHooks 内部也可能反查 SpawnManager 状态(取决于 reply-template 是否需要看 pool state)。

**当前状态**:未发现真循环 require(node module cache 容忍),但语义上反向 dependency 已经存在。

**建议**:
- 用 messageBus 解耦:SpawnManager publish `result.ready`,ThreadHooks subscribe + 跑 SystemAgent + publish `thread.metadata_updated`
- 或:把 result-after hooks 移到 SpawnManager 内部小函数(L2 内),ThreadHooks 只剩 reply-template 等纯 metadata hook

Phase 2F+ 评估。
