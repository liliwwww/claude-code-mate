## §13 marker 失败可观测性 ⏳ 待补

**问题**:本次 bug 时,H 输出包含 `<mate:handoff ... />` 但 MarkerDetector 返回 `[]`。**mate 完全没记录这个失败**。events 表里 0 个"识别失败"事件,前端 0 个错误提示。user 完全看不到 mate 在哪一步失败的。

**实施**:
- MarkerDetector 加一个 helper `looksLikeMarker(text)`:正则 `/\<mate:(handoff|done|blocked)\b/i` 检测**有意图**写 marker

  ```js
  {
    instanceId, threadSlug, projectId,
    textPreview: text.slice(0, 500),
    hint: 'looks like a marker but did not parse — check reason for unescaped " or other format issues',
  }
  ```
- dashboard tab 3 派工时序加 `marker.malformed` 类型(红条 + 文本预览)
- 顶栏 ticker 推一条 "⚠ marker 解析失败 · 详情查 tab 3"

**预估**:~80 行(MarkerDetector helper + SpawnManager publish + tab 3 渲染分支)。

## §14 eventType 真理源唯一化 ⏳ 待补

**问题**:`eventType` 是什么算"一轮 result"?
- streamParser 拼:`'result/' + subtype`
- RoleInstance 检查:`=== 'result'`  ← 漏改导致 Bug 1
- SpawnManager 检查:`startsWith('result')`  ← 对的

**3 处表达,任何一处不同步就是 bug。**

**实施**:streamParser export 谓词函数,所有 caller 用这些:
```js
// server/spawn/streamParser.js
function isResult(eventType) { return typeof eventType === 'string' && eventType.startsWith('result'); }
function isAssistantFinal(eventType) { return eventType === 'assistant'; }
function isSystemInit(eventType) { return eventType === 'system/init'; }
function isStreamPartial(eventType) { return eventType === 'stream_event'; }
function isRateLimitEvent(eventType) { return eventType === 'rate_limit_event'; }
function isUserEcho(eventType) { return eventType === 'user'; }
```

修改 caller:
- RoleInstance.js:`startsWith('result')` 改 `isResult(eventType)`(同时修复 Bug 1 还在的话)
- SpawnManager.js:`startsWith('result')` → `isResult(eventType)`,`=== 'rate_limit_event'` → `isRateLimitEvent(eventType)`
- 任何 hardcode `=== 'xxx'` 的地方都改

加单测:
- `streamParser.test.js` 加 6 个谓词测试

**预估**:streamParser ~40 行 + 5 处 caller 改 ~20 行 + 测试 ~30 行 = ~90 行。

## §15 marker 协议格式审视 ⏳ Phase 2F 评估

**问题**:reason 含 `"` 的 bug 这次靠正则 `(.*?)/is` 修了,但**根本性矛盾**:
- 协议用 XML attribute 语法 `target="X" reason="Y"`
- 用法是把整个 handoff brief(scope/invariants/acceptance/code snippets/JSON 例子/...)塞进 reason
- attribute 语法假设值是"短字符串无特殊字符";自由文本必然有 `"` `\n` `<` `>`等

新版正则修了 `"` 内嵌,但**还会撞**:
- reason 含 `</mate:handoff>` 子串(LLM 写 marker 例子时)
- reason 内嵌 markdown code fence ` ``` ` 含 `"`
- 极端:H 写 `reason="例如 <mate:done summary=\"ok\" />"` 想举例 marker 用法

**备选格式**:

**方案 A** — fenced syntax(打破 XML attribute 假设):
```
<mate:handoff target="mate-B">
对齐 hybrid_ontology 的 SSE 协议...
... (任意自由文本,允许任何字符)
</mate:handoff>
```
parse 简单:找 `<mate:handoff target="X">` 和 `</mate:handoff>` 配对,中间是 reason。

**方案 B** — JSON body:
```
<mate:handoff>
{
  "target": "mate-B",
  "reason": "对齐 hybrid_ontology...",
  ... 任何 JSON 字段
}
</mate:handoff>
```
parse:找 `<mate:handoff>...</mate:handoff>` 中间,JSON.parse。strict JSON 又强制 LLM 写转义,体验上可能不如 A。

**方案 C** — 维持现状,只是补正则容错(本次的 `.*?/is`)+ 加 §13 可观测性兜底

**评估维度**:
- LLM 写起来自然程度(A 最自然,C 中,B 要写 JSON)
- 解析鲁棒性(A B 高,C 中)
- 前端 marker strip 显示效果(A 最干净,B 显示 JSON 不友好)
- 向后兼容(C 完全兼容,A/B 需要 dual-parse 一段时间)
- 跟 mate role.md 教学一致性(A 改动最小)

**我倾向方案 A**。但**留待 Phase 2F user 拍板**,本轮先把 §12-§14 端到端质量保障做了,§15 改格式风险大于收益(现在正则修了能用)。

**实施(若 Phase 2F 采纳)**:
- MarkerDetector 改解析 + parse 元数据
- 4 个 mate-*.md 全部改例子展示
- 单测全套加 fenced format case
- 兼容期:dual-parse 旧 attribute + 新 fenced(2-4 周后弃旧)

## §11 mate 过程文件不侵入 sibling project ✅ 当前合规

**架构红线**(2026-06-13 user 拍板,architecture.md §6 #11):

mate 后端代码绝不能把"mate 自己的过程文件"(状态、协调、队列、临时、日志)写到任何 sibling project 目录内。child claude 在 sibling cwd 里读写代码是它干 sibling 的活,不算 mate 侵入。

**audit 结果**(2026-06-13):

| 检查项 | 结果 |
|---|---|
| `grep -rn "fs\." server/ \| grep -E "write\|append\|mkdir"` | 仅 2 处:`config.js mkdir(dataDir)` + `envCheck.js writeFileSync(probe to dataDir)` |
| 是否任何 fs 操作以 `projectRootDir` / `project.root_dir` 为前缀? | **0 hit** |
| `grep -rn "doc/_dispatch\|WORK_HANDOFF\|terminal_status\|doc/queue" server/` | **0 hit** |
| mate.sqlite 位置 | `D:\dev\claude_code_mate\data\mate.sqlite` ✓ |

**当前完全合规**。

**未来 audit grep 关键模式**(写进 CI / code review checklist):
```
grep -rn "fs\.write\|writeFileSync\|appendFile\|createWriteStream" server/ | grep -v "//"
# 每个写文件点都要 review:
# - 路径前缀必须是 config.paths.* 或 mate root,绝不能含 projectRootDir / project.root_dir
```

**违反后果**:任何写到 sibling 项目的"mate 过程文件"都会污染该项目 git 状态,user 看到不属于业务代码的文件被改 → 会撤销 → 数据丢失 → mate 重启后状态不一致。
